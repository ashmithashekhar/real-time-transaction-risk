# Real-Time Transaction Risk Platform

A streaming platform that scores payment transactions for fraud risk **as they happen** — combining transparent analyst rules with a machine-learning model in a single hybrid score, served both as a Kafka stream processor and as a FastAPI scoring API.

> **Data note:** every transaction in this project is **synthetic**, generated by the seeded generator in `src/data_generator.py`. No real customer, bank, or employer data is used anywhere. All evaluation numbers below were measured on synthetic data and are **not** evidence of performance on real transactions.

---

## Overview

Card fraud has to be caught in the window between authorisation and settlement, and a single technique is rarely enough: rules are explainable but brittle, models capture interactions but can be opaque. This platform runs both on every transaction:

1. A **synthetic transaction generator** simulates a realistic payment stream — per-user spending profiles, plus injected fraud typologies (account takeover, velocity bursts, card testing).
2. Transactions are published to **Kafka** and consumed by a **streaming scorer**; a **Spark Structured Streaming** job provides the same velocity-aggregation layer in a distributed form.
3. Each transaction gets a **rule score** (interpretable signals like *new device*, *international*, *extreme velocity*) and a **model score** (RandomForest trained on synthetic data), blended into one risk score with an `approve / review / block` decision.
4. Feature engineering lives in **one shared module** used by training, streaming, and the API — so the model never sees different features in production than it was trained on (no training/serving skew).

**Component map**

| Component | File | Role |
|---|---|---|
| Data generator | `src/data_generator.py` | Seeded synthetic users + transactions with labelled fraud patterns |
| Feature engineering | `src/features.py` | Single source of truth: features, rule signals, velocity tracker |
| Hybrid scorer | `src/scoring.py` | Blends rule score and model probability; decision bands |
| Training | `src/train_model.py` | Trains/evaluates the model, saves bundle + metrics metadata |
| Producer | `src/producer.py` | Publishes generated transactions to Kafka |
| Consumer | `src/consumer.py` | Scores the Kafka stream (or a broker-free `--simulate` replay) |
| Spark job | `src/spark_streaming_job.py` | Structured Streaming per-user velocity aggregation + alerts |
| API | `src/api.py` | FastAPI `/score` and `/health` endpoints |

**Cloud mapping (design note):** the local components map directly onto AWS — Kafka → Amazon MSK, the Spark job → EMR Spark Streaming, the API → ECS Fargate or Lambda behind API Gateway, model artefacts → S3, velocity state → DynamoDB/ElastiCache. Infrastructure code for AWS is intentionally out of scope for this repository; the pipeline itself is cloud-agnostic.

## Features

- Seeded, reproducible synthetic data with three injected fraud typologies and realistic per-user behaviour
- Interpretable rule engine — every alert lists the exact signals that fired and why
- ML model (RandomForest) trained through the *same* feature code used at serving time
- Hybrid decision bands: `approve` (< 40), `review` (40–69), `block` (≥ 70)
- Graceful degradation: with no trained model, everything still runs rules-only; with no Kafka broker, `--simulate` replays the identical scoring path
- Kafka producer/consumer with clear, actionable error messages when a broker is unreachable (compatible with kafka-python 2.x and 3.x)
- Spark Structured Streaming velocity job that explains its own setup and exits cleanly when PySpark is absent
- 20 automated tests covering features, rules, the generator, the scorer, and the API

## Quickstart

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

### 1 — Generate data and train the model

```bash
python -m src.data_generator --n 20000 --seed 42 --out data/transactions.csv
python -m src.train_model --n 20000 --seed 42
# (train_model can also generate its own data, as shown, or take --data <csv>)
```

### 2 — Score a stream without any infrastructure

```bash
python -m src.consumer --simulate --count 300
```

### 3 — Run the full Kafka pipeline

```bash
docker compose up -d                              # Kafka on localhost:9092
python -m src.producer --count 1000 --interval 0.05
python -m src.consumer                            # in a second terminal
```

### 4 — Serve the scoring API

```bash
uvicorn src.api:app --port 8000
```

```json
  "home_country": "US",
  "distance_from_home_km": 5600

```

Response (actual output of this request against a locally trained model):

```json
{
  "transaction_id": null,
  "rule_score": 100,
  "model_score": 99.5,
  "risk_score": 99.7,
  "decision": "block",
  "signals": [
    {"name": "high_amount", "weight": 20, "detail": "Amount $2,450.00 >= $1,000"},
    {"name": "international", "weight": 20, "detail": "Transaction country GB != home country US"},
    {"name": "night_transaction", "weight": 10, "detail": "Transaction at 03:15 local time"},
    {"name": "new_device", "weight": 15, "detail": "Device not previously seen for this user"},
    {"name": "high_risk_category", "weight": 20, "detail": "Merchant category 'gift_cards' is high risk"},
    {"name": "far_from_home", "weight": 12, "detail": "5,600 km from the user's home area"},
    {"name": "large_card_not_present", "weight": 10, "detail": "Card-not-present amount $2,450.00 > $500"}
  ]
}
```

A routine grocery purchase, by contrast, scores `risk_score: 0.0, decision: "approve"` with no signals. Interactive docs are available at `/docs` when the service is running.

## Scoring design

**Rule signals** (weights sum, capped at 100): very high amount ≥ $3,000 (+35) · high amount ≥ $1,000 (+20) · international (+20) · extreme velocity ≥ 5 txns/hour (+25) · elevated velocity ≥ 3 (+12) · new device (+15) · night transaction 00:00–04:59 (+10) · high-risk merchant category (+20) · far from home > 1,000 km (+12) · large card-not-present (+10).

**Blend:** `final = 0.65 × model_score + 0.35 × rule_score` when a model is loaded, otherwise the rule score alone. Thresholds are module-level constants in `src/scoring.py` — in a real portfolio they would be tuned to alert-review capacity and observed loss rates.

## Model evaluation (synthetic data — read the caveat)

Measured by `python -m src.train_model --n 20000 --seed 42` on this codebase (20,004 generated transactions, 1.52% fraud; 80/20 stratified hold-out, n = 4,001):

| Metric (hold-out) | Value |
|---|---|
| ROC-AUC | 0.9994 |
| PR-AUC | 0.9817 |
| Fraud precision @ 0.5 | 0.981 |
| Fraud recall @ 0.5 | 0.852 |
| Fraud F1 @ 0.5 | 0.912 |

Top feature importances: `card_not_present` (0.211), `category_risk` (0.167), `amount` (0.121), `log_amount` (0.119), `payment_risk` (0.113).

> **Caveat:** these numbers are high because the synthetic fraud patterns are programmatic and therefore cleaner and more separable than real fraud, which adapts and overlaps heavily with legitimate behaviour. Treat them as a pipeline correctness check, not a performance claim. Full run metadata is written to `models/model_metadata.json` on every training run.

In a streaming simulation of 302 transactions (seed 42, hybrid mode), decisions were: 296 approve (98.0%), 2 review (0.7%), 4 block (1.3%).

## Spark Structured Streaming job

`src/spark_streaming_job.py` reads the same Kafka topic, computes per-user 1-hour event-time window counts/sums with a 10-minute watermark, and emits high-velocity windows (≥ 5 transactions or ≥ $5,000 per hour) to the console. It needs a JDK and `pip install pyspark`; without them it prints a setup explanation and exits cleanly:

```bash
spark-submit --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1 \
  -m src.spark_streaming_job
```

## Limitations & production considerations

- **Synthetic data only.** Real deployment needs labelled historical transactions, point-in-time-correct feature computation, and drift monitoring.
- **Velocity state is in-memory** in the consumer/API reference implementations; production would use a shared state store (Redis, DynamoDB, or Kafka Streams state stores) so replicas agree.
- **Decision thresholds are illustrative constants**, not tuned operating points.
- The Spark job demonstrates the aggregation layer; a production version would sink aggregated features to a feature store consumed by the same scorer.
- No authentication, rate limiting, or PII handling is implemented in the API — it is a scoring reference service, and real deployments would add all three (the synthetic payloads here contain no real personal data).
